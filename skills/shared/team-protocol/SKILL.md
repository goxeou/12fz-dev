# 团队协作规则

> 这是摘要版。完整版查看 GitHub: `docs/协作规则.md` v1.7

## 角色分工

| 角色 | 核心职责 | 红线 |
|------|---------|------|
| 老板 | 策略设计、规则定稿、入金出金 | — |
| chaogu-ai | 交易信号执行/监控/止损、代码审查、文档维护、值班督导 | 不写业务代码、不碰数据库、不做开发实现 |
| 服务器技术 | 前端UI开发、阿里云运维(Nginx/SSL/MySQL)、生产部署回滚 | 不碰交易代码、不碰区块链/代币、不绕开chaogu-ai改生产配置 |
| gong3 | 后端PHP/Laravel开发、区块链代币、ESXi内网维护 | 不碰前端UI、不直接管阿里云生产（需经服务器技术或chaogu-ai确认） |

## 永久操作授权（/approve always）

老板可通过 `/approve always` 授予团队成员永久操作授权，被授权者不再需要逐次请示。

触发方式：老板说 `@xxx /approve always`

效果：
- 被授权者可在其职责范围内自主执行操作
- 不需每次操作前请示老板
- 授权内容按角色红线（见角色分工表）限定
- 授权撤销由老板口头指定

**当前已授权：** gong3（`/approve always`，2026-05-24）

## 时间统一规则

**🚫 所有用时间的地方必须统一使用北京时间（BJT, UTC+8）。** 这是硬性要求，不是装饰性约定。

### 检查清单

新部署一台机器或新增一个服务后，逐项确认：

| 检查项 | 标准 | 修复命令 |
|--------|------|---------|
| 系统时区 | `Asia/Shanghai` | `timedatectl set-timezone Asia/Shanghai` |
| `/etc/timezone` | 内容为 `Asia/Shanghai` | `echo "Asia/Shanghai" > /etc/timezone` |
| NTP同步 | `timedatectl show-timesync` 显示 yes | `apt install ntp` 或 `systemctl enable systemd-timesyncd` |
| Hermes cron | 用 `hermes_time.now()` 获取BJ时间 | 无需手动配，系统时区决定了 | |
| 物理时间 | `date` 输出含 `CST` | 修时区 |

### 陷阱：不要把 WebSocket 断连当成时区问题

Agents 的聊天消息时间戳来自飞书服务器，与本地系统时区无关。如果看到"最后消息在8小时前"：
1. ✅ 先查网关进程与 WebSocket 连接时间
2. ✅ 再查飞书 WebSocket 是否断连
3. ❌ 不要第一反应就去改时区

（详见 `references/agent-unresponsive-diagnosis.md` → "网关存活但消息时间戳是旧的"）

## 沟通规则

- 12FZ群发项目相关内容，交易信号走私聊发老板
- @后10分钟内回应"收到"或提问，否则其他人应主动排查
- 每天至少1次进展汇报
- 不代答、不刷屏、能加值才说话
- 所有时间用北京时间（BJT, UTC+8）

## 协作效率规则（v1.0 2026-05-24）

### 1. 响应超时机制

| 规则 | 说明 |
|------|------|
| 在线状态 | 每30分钟自动报一次 🟢 在线（共享状态文件或群消息） |
| @后超时 | 被 @ 后15分钟无回应 → 其他人直接接手，不等 |
| 连续失联 | 连续3次超时 → 群里 @ 老板 |

### 2. 权限去中心化

关键权限至少两人持有，不依赖单点：
- 新机/旧机 root 密码统一
- Docker、Nginx、MySQL 管理权至少两人有
- 开工前老板一次给齐所有人所需权限

### 3. 任务分配闭环

| 动作 | 必须回复 |
|------|---------|
| 被 @ 分配任务 | `✅ 收到` |
| 任务完成 | `✅ [任务名] 完成` |
| 卡住 | `🔴 [卡住原因]` + @能解决的人 |

### 4. 并行最大化

- 每个任务标注：🔵 并行 / 🔴 串行（等什么）
- 瓶颈任务之外必须塞满其他工作
- 估时 = 最长串行路径时间 + 20% buffer

### 5. 时间统一（已执行）

- ✅ poller 轮询器已修（强制 UTC→BJT）
- ✅ 三台服务器时区全部 Asia/Shanghai
- 新脚本禁止裸用 `datetime.fromtimestamp()`

### 进度汇报规则

- **先搞定再统一推** — 除非老板主动问，否则不用中间进度汇报。全部做完一次性汇总通知老板
- 群内对老板的回复保持简短，结论先行，不需要分段报进度
- 多人协作的任务，各自完成后由chaogu-ai汇总统一汇报，不各自找老板报

### 多角色协作方法论（参考）

完整的多角色任务分配、瓶颈分析、并行执行、进度同步方法论见 `devops/server-migration-planning` 技能 → `references/work-allocation-template.md`。

核心原则：
1. **先找瓶颈** — 最长串行数据管道决定总时间，不是所有任务之和
2. **瓶颈期塞满** — 无依赖的事先干不等，所有能并行的事在瓶颈期做完
3. **权限前置** — 开工前一次性给齐 SSH/数据库/访问权限
4. **确认闭环** — 分配任务必须 @当事人，等人回复"收到"才算数

### ⚠️ 关键：汇总意见时禁止依赖压缩摘要

**教训（2026-05-23）：** 老板问大家意见时chaogu-ai压缩成"目前仅chaogu-ai发言，其他人未回应"。但服务器技术和gong3都回了。摘要写错→一路错下去。

**规则：**
1. 涉及"谁说了什么、谁没回应"等事实判断，**不信任上下文压缩摘要**
2. 必须**查询原始对话记录**逐一确认后再下结论
3. 汇总后发出去之前，再扫一遍原始记录做双重校验

- 各机器cron `*/10 * * * *` git pull（主方案）
- Vultr cron `*/15 * * * *` 主动通过222 SSH推送到gong3（备选，不依赖gong3网络）

## 工作流

```\n老板决策 → chaogu-ai拆解需求 → 推送GitHub\n   ↓\n服务器技术(前端) ← → gong3(后端)\n   ↓\n合入前自己开Chrome看效果 → 截图发群\n   ↓\nchaogu-ai代码审查 + 浏览器实测\n   ↓\n合入dev → 汇报老板\n```

## 保护与恢复三条铁律

1. **改前备份** — 配置文件必须`cp xxx.conf.bak.$(date +%Y%m%d_%H%M%S)`，数据库必须先mysqldump
2. **改中通报** — 操作前群里@所有人说明范围，改完观察15分钟无异常再离开
3. **改后验证** — 不改完就走，必须验证服务正常再关终端

### ⚠️ 关键：不要多人同时操作同一份配置

**教训（2026-05-24 NPS事故）：** 多人同时在阿里云上修改NPS配置，备份文件被覆盖，去重脚本运行时数据已变，最终不得不从最原始的 `.bak` 文件恢复。

**规则：**
1. 修改共享配置前先在群里说"我要改X"
2. 其他人等前一个人改完验证完再动
3. 有正在进行的操作时，其他成员不得同时修改同一文件

### 权限边界速查

| 操作 | 谁可以 | 需确认 |
|------|--------|-------|
| 改dev分支 | gong3+服务器技术 | chaogu-ai审查 |
| 改main分支 | 仅chaogu-ai | 老板确认 |
| 改NPS隧道 | 仅chaogu-ai | 群内通报 |
| 改阿里云Nginx/SSL | 仅服务器技术 | 群内@所有人 |
| 改生产数据库 | 无 | 老板+全群确认 |

## 视觉验证规范

**所有人适用，合入前必须执行：**

| 角色 | 写什么 | 谁验证 | 方式 |
|------|--------|--------|------|
| 服务器技术 | 前端UI | 自己开Chrome看 | 截图发群 |
| gong3 | 后端/插件（有界面的） | 自己开Chrome看 | 截图发群 |
| chaogu-ai | 代码审查 | 浏览器实测一遍 | 截图附审查报告 |

**红线：**
- ❌ 不开浏览器看实际效果就说"应该可以"
- ❌ 跳过视觉验证直接合入

**核心一句：合入前截图发群，证明你打开看过。**

## 文档发布流程

> 教训（2026-05-24）：老板给的按钮排查规范是"讨论稿"，chaogu-ai误直接推了GitHub。被纠正：讨论稿先汇总等老板确认。

| 阶段 | 操作 | 谁做 |
|------|------|------|
| 讨论中 | 老板/团队发言 → 整理为草案 | chaogu-ai |
| 汇总 | 列要点 → 发群里汇总 → 等老板"确定" | chaogu-ai |
| 已确定 | 老板说"确定"/"可以" → 才推GitHub | chaogu-ai |
| 讨论稿 | 未确认的内容 → 仅本地存reference | 所有人 |

**红线：** 未等老板确认的讨论稿/草案，**不推GitHub**。仅汇总发群待确认。
