## 第五部分：支付体系

### 5.1 架构设计 — 插拔式支付渠道

```
┌─────────────────────────────────────────────────┐
│              12FZ 支付管理中心                    │
│  （国家-支付矩阵 / 默认全开 / 按需关闭）            │
├────────┬────────┬────────┬────────┬──────────────┤
│        │        │        │        │              │
│ 支付宝  │BNB Pay │PayPal  │12FZ代币│ 新支付X...   │
│ 插件    │ 插件   │ 插件   │ Gateway│ 插件         │
│        │        │        │        │ (1天接入)    │
└────────┴────────┴────────┴────────┴──────────────┘
```

**统一基类：** `SZ_Payment_Gateway` 继承 `WC_Payment_Gateway`
**新渠道接入：** 写一个类继承基类 + API密钥 = 1天上线

### 5.2 国家-支付管控矩阵

```
                ┌─── 中国 ─── 美国 ─── 日本 ─── ...
                │
  支付宝        │   ✅      ❌      ❌
  Binance Pay   │   ✅      ✅      ✅  ← 新增
  PayPal        │   ❌      ✅      ✅
  12FZ代币      │   ✅      ✅      ✅
  信用卡        │   ✅      ✅      ✅
  ⋮             │
```

- **默认全开**（所有支付方式对所有国家可用）
- 按需手动关闭（取消勾选即禁用）
- 用户结算时按收货国家自动过滤

### 5.3 支付排序规则

排序支持**按国家独立配置**：

| 规则 | 说明 |
|------|------|
| 全局默认排序 | 所有国家统一的排序 |
| 按国家定制 | 某国家单独设置排序（覆盖全局） |
| 使用人次排序 | 可选一键按支付量降序排列 |

**默认顺序：** 支付宝 → Binance Pay → PayPal → 12FZ代币 → 信用卡 → ...

### 5.4 数据库设计

```sql
-- 支付禁用表（默认全开，只存禁用的）
CREATE TABLE sz_12fz_disabled_payments (
    id         INT AUTO_INCREMENT PRIMARY KEY,
    country    VARCHAR(4)   NOT NULL,
    gateway_id VARCHAR(32)  NOT NULL,
    UNIQUE KEY uk_disabled (country, gateway_id)
);

-- 支付排序表
CREATE TABLE sz_12fz_payment_ordering (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    country     VARCHAR(4)   NOT NULL,
    gateway_id  VARCHAR(32)  NOT NULL,
    sort_order  INT          NOT NULL DEFAULT 0,
    UNIQUE KEY uk_order (country, gateway_id)
);

-- 支付使用统计
CREATE TABLE sz_12fz_payment_stats (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    country     VARCHAR(4)   NOT NULL,
    gateway_id  VARCHAR(32)  NOT NULL,
    usage_count INT          NOT NULL DEFAULT 0,
    updated_at  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_stats (country, gateway_id)
);
```

## 附录 P：团队分工细化与运维知识库原则（v5.0）

> 2026-05-25 23:19-23:50 CST，老板在「12FZ程序开发组」群内确认以下决策

### P.1 团队分工细化

| 决策 | 内容 | 来源 |
|------|------|------|
| 1 | **维修技能由@服务器技术 负责** — 其他bot出问题，由服务器技术负责修复。明确分工「大家出问题，服务网技术维修」。 | 老板确认（MSG 238） |
| 2 | **gong3的工作由@chaogu-ai 分配** — gong3不自主认领任务，等待chaogu-ai分配后执行。 | 老板确认（MSG 308：「工作由@chaogu-ai 分配,你要问他」） |
| 3 | **相互不影响的工作应该并行** — 老板发现gong3和服务器技术的工作没有并行，指出后要求调整。 | 老板确认（MSG 159：「相互不影响的工作为什么没有并行」） |

### P.2 故障知识库管理原则

| 决策 | 内容 | 来源 |
|------|------|------|
| 1 | **只保留有明确解决结果的故障条目** — 实验性/未解决的问题不纳入知识库。 | 老板确认（MSG 258：「以后要能自动收集遇到问题，必须有解决结果的」） |
| 2 | **磁盘扩容问题不纳入知识库** — 认为是底层操作问题，不应作为修复技能。 | 老板确认（MSG 270：「我的意思是磁盘不纳入」） |
| 3 | **自动收集问题机制** — 未来要能自动收集问题，但只保留有解决结果的条目。 | 老板确认（MSG 258） |

### 影响

- ✅ 团队分工更清晰：服务器技术=运维/故障修复/技能维护，chaogu-ai=分配/协调/审核，gong3=按分配执行
- ✅ 知识库质量提升：只保留有解决方案的有用条目
- ✅ 避免知识库被无关条目（如磁盘扩容）污染
