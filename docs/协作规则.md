## 工作流与分工边界

### 任务发起 → 完成全流程

```
老板决策 → chaogu-ai拆解文档/需求 → GitHub推送通知
                                      ↓
              服务器技术(前端) ← → gong3(后端)
                    ↓                      ↓
              chaogu-ai代码审查 + 浏览器实测
                    ↓
              合入dev → 汇报老板
```

### 跨域操作的协调规则（为防止再发生NPS事故）

| 场景 | 谁操作 | 必须先通知谁 | 说明 |
|------|--------|-------------|------|
| 改阿里云Nginx/证书/生产配置 | 服务器技术 | 群里@所有人 | 选低峰期，提前备份 |
| 改阿里云数据库 | gong3（设计）+ 服务器技术（执行） | 群里@所有人 | 先mysqldump再改 |
| 改Vultr配置 | chaogu-ai | 群里通报 | 涉及VPN/交易服务 |
| 改ESXi(gong3)配置 | gong3 | 群里通报 | 内网环境 |
| 改GitHub仓库文档 | 谁更新谁推 | — | 确保不是只改本地 |
| 改WordPress(12fz.com) | 服务器技术（前端）/ gong3（后端） | chaogu-ai审核 | 必须走Staging→生产 |
| 改交易策略/持仓 | chaogu-ai | 走私聊只汇报老板 | 不在群里讨论 |

### 边界裁定（有争议时按此规则裁决）

1. **前端vs后端边界模糊** → 模板/视觉类归服务器技术，逻辑/数据处理类归gong3
2. **需要跨域修改** → 由chaogu-ai协调，不能自己跨过去直接改
3. **谁都觉得不该自己做的** → chaogu-ai汇报老板决定

## 二、沟通规则

### 2.1 群聊规范
- **12FZ程序开发组** 只发12FZ项目相关内容（开发进度/代码审核/需求讨论）
- 交易信号、策略报告、仓位状态等 **走私聊** 发老板
- 被点名或被问到时才说话，不代答
- 不替别人回答问题
- 能加值才发言，不刷屏
- **群里所有时间统一使用北京时间（BJT, UTC+8）**

### 2.2 响应时效要求

| 场景 | 时限 | 处理方式 |
|------|------|---------|
| 被@分配任务 | **10分钟内** | 回复"收到"或明确提问 |
| 每日进展汇报 | **每天至少1次** | 简单说明在做什么、进度、卡点 |
| 遇到不确定的问题 | **立即** | 群里提问，不自己猜 |
| 老板直接提问 | **立即** | 知道就答，不知道就说不知道 |

**超时处理：**
- 被@后10分钟无回应 → chaogu-ai 主动查远程状态
- 超过1小时无回应 → 按值班故障处理流程
- 连续2天无任何汇报 → chaogu-ai 汇报给老板

### 2.3 Bot互通机制
- 群内三bot通过轮询方案互通（3秒轮询拉群消息→本地缓存）
- 小问题bot间直接沟通，大决策找老板

### 2.4 值班监控规则

#### chaogu-ai 的督导职责
- 群内任何人设备故障或长时间未汇报工作，@chaogu-ai 后 **10分钟** 无明确回应 → chaogu-ai 查询其远程信息，SSH连接检查 Hermes 与飞书连接问题

#### 服务器技术的备份督导职责
- 如果 **@chaogu-ai 超过1小时** 没有在群里督导工作 → @服务器技术 远程查看 chaogu-ai 的服务器（Vultr），检查 Hermes 与飞书连接问题并修复

## 四、开发流程规范（附录B v3.2）

### 4.1 讨论阶段
1. **讨论阶段不准写代码**
2. 讨论达成一致后，由 chaogu-ai 更新文档 → 推 GitHub
3. 推送后，开发者**必须通读全部文档**再开始写代码
4. 文档统一维护，不各自保留版本

### 4.2 双向提醒机制
- 文档更新后，chaogu-ai 在群里通知相关人
- 开发者对文档有疑问，及时在群里提出

### 4.3 分支策略

| 分支 | 用途 |
|------|------|
| `main` | 生产可用版本 |
| `dev` | 开发集成分支 |
| `feature/*` | 功能开发分支 |
| `docs/*` | 文档更新分支 |

### 4.4 完成标准（DoD）
- [ ] 代码能跑通
- [ ] 代码审查通过（chaogu-ai 审核）
- [ ] 文档已更新
- [ ] 已合入 `dev` 分支

### 4.5 版本号规范
- 格式: `v主版本.次版本.修订号`
- 同步更新 Changelog

### 4.6 代码审查流程
1. chaogu-ai 负责代码审核
2. 审核内容：找bug + 文档一致性检查
3. 审核环节增加**浏览器实地测试**：
   - 注册→登录→上架→下单→支付 全流程跑通
   - 每步截图记录

### 4.7 进度汇报
- 有进度才发，没有进度不刷屏
- 进度更新发在12FZ程序开发组

## 八、配置修改保护与恢复机制

> 本版纳入服务器技术和gong3意见后完善。核心底线：改前备份、改中确认、改后验证、留恢复窗口。

### 8.1 操作底线（三条铁律 — 来自gong3）

1. **改前备份** — 任何配置修改前，`cp` 备份是底线操作，不备份不操作
2. **改完先验证再重启** — 修改配置后先检查语法/配置合法性，确认正确再重启服务
3. **高风险操作提前群确认** — 涉及SSH/MySQL/NPS/nginx等关键服务的修改，提前在群里@所有人确认

### 8.2 操作前（预防 — 整合）

| 层级 | 措施 |
|------|------|
| 配置文件 | 修改前必须 `cp xxx.conf xxx.conf.bak.$(date +%Y%m%d_%H%M%S)` |
| 数据库 | 改表结构前先 `mysqldump` 全量备份 |
| 代码 | 必须走Git分支，不能直接改线上代码 |
| NPS隧道 | 改前通过API导出全量隧道清单备份 |
| 其他关键配置 | 操作前先在群里通报"要改X，影响Y"，@所有人确认后再操作 |
| 大批量改动 | 先改1条测试验证，通过后再批量执行 |

### 8.3 自动备份机制（来自服务器技术 + gong3）

两种备份频率互补运行：

| 备份类型 | 频率 | 范围 | 保留期 | 实施者 |
|----------|------|------|--------|--------|
| **快速快照** | 每小时 | 关键配置文件（见附录A） | 24小时 | chaogu-ai在Vultr上配置cron |
| **每日全量** | 每天00:00 BJT | 关键配置文件+数据库 | 7天 | /mnt/data/12fz/backup/config/ |

备份脚本统一放在 `/root/scripts/config-backup.sh`（Vultr）和对应位置（阿里云），从GitHub仓库 `scripts/` 目录同步。

### 8.4 毁损检测与自动报警（来自服务器技术）

配置文件被意外清空或缩小时需要自动感知：

| 检测项 | 检测方式 | 报警方式 |
|--------|---------|---------|
| 配置文件大小异常 | cron每5分钟检查文件大小，低于阈值触发 | 群内@责任人 |
| 服务异常停止 | 检查进程是否存在 | 群内通知 |
| 磁盘空间不足 | 检查 `df -h` | 群内通知 |

实现：chaogu-ai在Vultr配置检测脚本，检测到异常自动在群内发消息。

### 8.5 操作日志（来自服务器技术）

每次谁改了关键配置，自动记录一条日志：

- 日志位置：`/var/log/12fz/ops.log`
- 日志格式：`[时间] 操作者@机器: 操作内容 (备份路径)`
- 包括：配置修改、服务重启、数据库变更、文件删除
- 手动操作也建议在群里说明后自行记入

### 8.6 恢复预案优先级（来自gong3）

当配置损坏或误删时，按以下优先级恢复：

1. **优先从备份恢复** — 从 `/mnt/data/12fz/backup/config/` 或 `.bak` 备份中恢复
2. **无法通过文件恢复但API可用** — 使用管理API重建（如NPS隧道）
3. **文件和API都不可用** — 通过Web管理后台手动重建

> 例：2026-05-23 NPS事故中，tasks.json被清空（无备份），通过NPS API `/index/add/` 重建全部22条隧道恢复服务。

### 8.7 事故复盘（2026-05-23 NPS事故）

- **根因**：tasks.json为`*#*`分隔特殊格式，不兼容标准JSON编辑工具导致文件清空
- **教训**：操作前未备份；直接编辑运行中的关键配置文件
- **改进措施**：
  - 已通过NPS API `/index/add/` 重建所有隧道并验证上线
  - 建立本规则第八节全量保护机制
  - 关键配置清单明确标注风险等级（见附录A）
  - 所有机器统一配置自动备份脚本

## 九、Bot健康监控系统

> 2026-05-24 补充。基于服务器技术内存爆满+日志膨胀+无人发现的教训，建立三层防线。

### 9.1 第一层：自检（每个Bot管好自己）

部署在每台机器上的自检脚本 `/root/scripts/health-check.sh`（从GitHub同步），每10分钟（cron）执行：

| 检查项 | 阈值 | 异常处理 |
|--------|------|---------|
| Hermes gateway进程 | 至少1个 | 尝试重启 `systemctl restart hermes` |
| 最近5分钟有无消息处理 | 日志中有新行 | 超时视为卡住 → 重启gateway |
| poller.log/error.log | < 100MB | 超过则 `truncate -s 0` 并压缩归档 |
| 内存占用 | < 80% | 超过则清理缓存并告警 |
| 磁盘空间 | < 85% | 清理/tmp和旧日志 |

自检通过 → 静默（不出声）
自检发现异常 → 尝试自动恢复 + 群里@责任人告知

### 9.2 第二层：互检（chaogu-ai监控服务器技术和gong3）

chaogu-ai（Vultr）配置cron，每15分钟SSH远程检查：

| 检查目标 | 检查方式 | 告警条件 |
|---------|---------|---------|
| 服务器技术（阿里云） | SSH远程 `systemctl is-active hermes` | 进程不在 → @服务器技术 |
| gong3（ESXi） | 通过NPS隧道SSH | 连接超时 → @gong3 |
| 两台机器的日志大小 | SSH远程 `ls -lh` | 日志>100MB → @责任人 |
| 两台机器的磁盘+内存 | SSH远程 `df -h` `free -h` | 异常 → @责任人 |

互检每15分钟跑一次，正常则静默。连续3次（45分钟）检测到同一异常但没有修复 → 群里@老板。

### 9.3 第三层：兜底（chaogu-ai挂了谁来盯）

将协作规则7.1的文字规则落地为脚本：

| 兜底角色 | 触发条件 | 行动 |
|---------|---------|------|
| 服务器技术 | chaogu-ai超过1小时未在群督导 | 远程SSH查Vultr，修复Hermes连接 |
| gong3 | 服务器技术也沉默超过30分钟 | 同时查阿里云+Vultr |
| 老板 | 三个Bot都沉默超过2小时 | 群里或私聊手动重启 |

### 9.4 恢复流程

当Bot卡死或宕机时：

1. 优先自动恢复（gateway重启）
2. 自动失败 → 同机器其他Bot远程检查（三台机器上都有sshpass）
3. 远程也失败 → 群里@老板报修

## 十、中央技能库管理

> 2026-05-24 补充。所有Bot的技能统一托管在 GitHub，自动同步到各机器。

### 10.1 技能分类

| 类型 | 内容 | 存放 | 同步方式 |
|------|------|------|---------|
| 🟢 **公共技能** | 所有Bot共享（协作规则/健康检查/服务器信息/备份恢复） | GitHub `skills/shared/` | 每台机器自检时自动拉取 |
| 🟡 **角色技能** | 按角色分工（chaogu-ai/服务器技术/gong3各自专属） | GitHub `skills/roles/` | 自动拉取，按主机名识别角色 |
| 🔴 **本地敏感技能** | 含SSH密码/API密钥/内网信息 | 仅本地机器 | 手动维护，不上GitHub |

### 10.2 同步机制

- 同步脚本: `/root/scripts/skill-sync.sh`（从GitHub `scripts/skill-sync.sh`同步）
- 自动触发: 集成在 `health-check.sh` 自检脚本中，每10分钟运行
- 手动触发: `bash /root/scripts/skill-sync.sh`

### 10.3 创建/修改技能

1. 在 GitHub `skills/shared/`(公共) 或 `skills/roles/`(角色) 下创建 `<技能名>/SKILL.md`
2. 更新 `skills/index.md` 清单
3. 推送到GitHub
4. 自检脚本在10分钟内自动同步到所有机器

### 10.4 命名规范

- kebab-case（小写+短横线）
- 公共技能用领域名: `team-protocol`, `ops-backup`
- 角色技能用角色名: `chaogu-ai`, `server-tech`, `gong3`
- 超过2人使用的公共技能 → 必须放在 `skills/shared/`
