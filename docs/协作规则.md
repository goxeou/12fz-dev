## 二、沟通规则

### 2.1 群聊规范
- **12FZ程序开发组** 只发12FZ项目相关内容（开发进度/代码审核/需求讨论）
- 交易信号、策略报告、仓位状态等 **走私聊** 发老板
- 被点名或被问到时才说话，不代答
- 不替别人回答问题
- 能加值才发言，不刷屏
- **群里所有时间统一使用北京时间（BJT, UTC+8）**

### 2.2 响应时效要求

| 场景 | 时限 | 处理方式 |
|------|------|---------|
| 被@分配任务 | **10分钟内** | 回复"收到"或明确提问 |
| 每日进展汇报 | **每天至少1次** | 简单说明在做什么、进度、卡点 |
| 遇到不确定的问题 | **立即** | 群里提问，不自己猜 |
| 老板直接提问 | **立即** | 知道就答，不知道就说不知道 |

**超时处理：**
- 被@后10分钟无回应 → chaogu-ai 主动查远程状态
- 超过1小时无回应 → 按值班故障处理流程
- 连续2天无任何汇报 → chaogu-ai 汇报给老板

### 2.3 Bot互通机制
- 群内三bot通过轮询方案互通（3秒轮询拉群消息→本地缓存）
- 小问题bot间直接沟通，大决策找老板

### 2.4 值班监控规则

#### chaogu-ai 的督导职责
- 群内任何人设备故障或长时间未汇报工作，@chaogu-ai 后 **10分钟** 无明确回应 → chaogu-ai 查询其远程信息，SSH连接检查 Hermes 与飞书连接问题

#### 服务器技术的备份督导职责
- 如果 **@chaogu-ai 超过1小时** 没有在群里督导工作 → @服务器技术 远程查看 chaogu-ai 的服务器（Vultr），检查 Hermes 与飞书连接问题并修复

## 四、开发流程规范（附录B v3.2）

### 4.1 讨论阶段
1. **讨论阶段不准写代码**
2. 讨论达成一致后，由 chaogu-ai 更新文档 → 推 GitHub
3. 推送后，开发者**必须通读全部文档**再开始写代码
4. 文档统一维护，不各自保留版本

### 4.2 双向提醒机制
- 文档更新后，chaogu-ai 在群里通知相关人
- 开发者对文档有疑问，及时在群里提出

### 4.3 分支策略

| 分支 | 用途 |
|------|------|
| `main` | 生产可用版本 |
| `dev` | 开发集成分支 |
| `feature/*` | 功能开发分支 |
| `docs/*` | 文档更新分支 |

### 4.4 完成标准（DoD）
- [ ] 代码能跑通
- [ ] 代码审查通过（chaogu-ai 审核）
- [ ] 文档已更新
- [ ] 已合入 `dev` 分支

### 4.5 版本号规范
- 格式: `v主版本.次版本.修订号`
- 同步更新 Changelog

### 4.6 代码审查流程
1. chaogu-ai 负责代码审核
2. 审核内容：找bug + 文档一致性检查
3. 审核环节增加**浏览器实地测试**：
   - 注册→登录→上架→下单→支付 全流程跑通
   - 每步截图记录

### 4.7 进度汇报
- 有进度才发，没有进度不刷屏
- 进度更新发在12FZ程序开发组

## 五、安全规范

### 5.1 安全等级

| 等级 | 说明 | 处理方式 |
|------|------|---------|
| P0 | 资金安全相关 | 立即处理，先停再修 |
| P1 | 用户数据/支付流程 | 24小时内修复 |
| P2 | 功能体验类 | 排期修复 |

### 5.2 开发安全
- 币安API安全优先，宁愿慢也不能被封
- 策略扫描等统计类任务可以慢，安全第一
- 系统升级/配置变更前确保有回滚方案
- 数据真实性必须交叉验证——至少2个数据源，标注来源和置信度

## 七、值班与故障处理

### 7.1 故障响应流程

被@后10分钟无回应 → chaogu-ai查远程
chaogu-ai超1小时未督导 → 服务器技术查chaogu-ai

### 7.2 常见故障排查
- Hermes Agent 进程是否存在 → `systemctl status hermes`
- 飞书连接是否正常 → 检查 gateway 日志
- xray VPN是否在线 → 检查 `ss -tlnp | grep xray`
- 网络连通性 → `curl -s --connect-timeout 5 https://open.feishu.cn`
